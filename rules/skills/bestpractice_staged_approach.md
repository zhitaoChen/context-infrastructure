# 分阶段工作法（Staged Approach）

## 元数据

- **类型**: BestPractice
- **适用场景**: AI 辅助自动化、批量处理、破坏性操作
- **创建日期**: 2026-02-21
- **来源**: 2026-01-07 观察记录

---

## 核心框架

将复杂自动化任务分解为三个阶段：

```
Stage 1: 数据采集 → Stage 2: 批量处理 → Stage 3: 确认与发布
```

### Stage 1: 数据采集

- 完整拉取源数据到本地
- 与线上系统隔离
- 数据落盘后才进入下一阶段
- 目标：确保后续处理有稳定的数据基础

### Stage 2: 批量处理

- 在本地环境调用 AI
- 与线上系统完全隔离
- 可重复执行、可回滚
- 目标：在安全沙盒中完成 AI 非确定性操作

### Stage 3: 确认与发布

- 人工审核处理结果
- 一键发布或批量应用
- 记录变更日志
- 目标：人为把关最后一道防线

## 核心原则

### 真实样本与阶段验收

依赖外部输入时，先验证来源可访问、目标输入确实获得，并用一个真实样本完成必要转换，
再决定批量处理和复用。缺少真实输入时可交付设计或模拟验证，但不能声称真实链路已完成；
样本成功也不能代替批量质量、异常恢复和规模约束的验证。

分别报告输入获取、实际处理、产物生成、质量验收和正式生效状态，附当前可检查的
文件或记录，以及未完成项。用户只要求采集时，完成采集就是该任务终点，不擅自增加发布。

涉及批量状态更新时，先验证输入 ID 完整、唯一、无未知项，再整体提交；
失败不部分消费输入，重试保持幂等。普通非批处理任务不强制套用 ID 契约。

### 数据转换的总体与缺失核对

转换采集结果或生成上传兼容文件时，先明确原始总体、记录标识和目标字段契约。
输出需与输入逐项核对标识及数量；失败、部分或缺失响应保留占位和状态，
不能将成功子集默认为完整数据。有意筛选的子集单独命名，列出排除条件和数量。

目标格式不支持富内容时，可按授权生成明确标注为有损的文本表示，保留原始结果及限制说明；
不得编造缺失响应或把占位记录计为成功。交付时核对输入、输出、排除、失败数量与字段校验结果。
原始请求、响应和项目数据留在目标项目，不因沉淀通用方法而复制到中央知识库。

### 常规升级受阻时的替代安装验证

存在官方替代发行包时，先确认失败原因、当前版本及各实际启动入口，不通过关闭证书或完整性校验绕过错误。核对官方校验信息后，在不替换现有入口的隔离位置测试；版本号、配置兼容、必要插件和真实功能请求分别验收，未测试项目明确列出。切换前保留可恢复的原入口与配置，验证失败停止切换。

这是一组验收约束，不证明任意替代包都兼容；缺少可信来源、校验信息、权限或回退条件时，保留现状并报告阻塞，不能把下载成功或版本输出当作升级完成。

### 评估实验的可比性与反例

评估功能变体时，先以小样本验证请求、响应获取、评分和结果解释的完整链路。
基线与变体应使用固定输入、相同上下文边界及一致评分口径，保留失败和未决样本；
缺少可比基线时只报告已验证结果，不声称改进。

比较前明确统计单元、总体、分母、判定规则和评分版本，例如全部轮次与每会话末轮不能混用。
来源归属、文本提及、首项次序与整体出现率等不同定义分别命名，不静默替换。
评分器判断是否合理与原始回答是否正确分开验收；缺少口径或依据时不声称可比。

分数变化需要与真实响应抽查相互印证，同时检查基线更好的反例。
评分不合理时先定位差异再调整评分方法，并重新评估，不以调参后的分数替代质量证据。
这是实验控制与验收要求，不代表这些操作已经证明能提升性能。

### 隔离-处理-验证闭环

```
线上环境 ←→ 本地沙盒 ←→ 人工确认
    ↓              ↓            ↓
   只读          AI 操作      发布决策
```

### Dry Run 优先

**任何破坏性操作前必须先 Dry Run。**

破坏性操作包括：
- 文件覆盖/删除
- 数据库写入
- API POST/PUT/DELETE
- 邮件/消息发送
- 任何不可逆操作

Dry Run 检查清单：
- [ ] 确认操作范围（影响哪些文件/记录）
- [ ] 确认操作内容（具体变更是什么）
- [ ] 确认可回滚（有备份或版本控制）
- [ ] 确认执行环境（不是生产环境）

## 典型应用场景

### 内容翻译与发布

1. Stage 1: 拉取待翻译内容到本地
2. Stage 2: 调用 AI 批量翻译，生成预览
3. Stage 3: 人工审核后一键发布

### 数据处理 Pipeline

1. Stage 1: 导出源数据（CSV/JSON）
2. Stage 2: AI 处理 + 校验
3. Stage 3: 确认后导入目标系统

### 批量代码修改

1. Stage 1: 创建独立分支
2. Stage 2: AI 执行修改 + 本地测试
3. Stage 3: Review 后合并
