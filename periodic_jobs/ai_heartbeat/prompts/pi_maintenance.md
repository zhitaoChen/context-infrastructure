# pi 会话内知识维护

此任务使用当前 pi 模型，不调用 Copilot CLI、gh 或独立模型进程。先读取仓库 README.md、AGENTS.md 与常驻入口、contexts/memory/INBOX.md、docs/CRONTAB.md，再检查 memory.py status。历史只使用本机已授权配置，不擅增来源或移动回补时间。

## 串行执行

1. fetch 并核对现有分支与上游，发现落后继续完成同步，不只报告。无本地提交时快进；重叠未提交修改先私有备份再三方恢复，双方都有提交则在原分支正常merge。自主合并可确定冲突并验证，语义取舍不明才报告具体问题。不创建新分支、不丢弃并发修改、不强推不变基；Git同步与可独立完成的私有整理分开验收。
2. 核对本机授权配置，以北京时间当天00:00至本轮扫描截止时间的全部已落盘历史为每日目标，读取真实用户消息及对应助手正文，不只抽样。旧 history.json／agent_history.json 存在且启用时，分页collect直到当日范围扫描完成；conversation_daily.json 沿用已有授权，以 conversation_review.prepare --days 1 建立当日完整清单，局部placeholder脱敏，不调用独立模型。未配置旧采集器不等于没有授权；不新增来源或移动授权回补时间。最近两分钟活跃记录延后复核，报告截止时间；最后复扫新增记录，跨午夜仍以本轮目标日期为准。
3. 程序先按可核验特征排除定时自动提示，不让自动提示占用人工语义审阅额度；不能仅因用户提到定时或自检就排除真实请求。真实对话按原始问答内容及会话去重；相同问题且助手回复不同仍须审阅，敏感字段脱敏后相同不能视为原文相同。重复版本仅保留首次代表，代表审阅成功后才记其重复项已处理；保留独立会话证据与长文本各分块。使用 conversation_review.show 分页查看已脱敏用户及完整助手正文，通过 conversation_review.commit、validate_output、来源复核和 history.apply_resolution 事务提交当前会话判断；旧引用通过 history.get_turn／history.resolve。分页大小只是控制上下文，不是每日总量上限。循环直到当日所有真实对话已审阅，敏感/不确定项保留 needs_review 并明确原因；失败或上下文不足应保存检查点并继续恢复，不把尚未审阅的内容记为完成。
4. 使用当前会话模型通过 memory.run_worker 执行 daily，严格采用 daily_decisions 验证。每轮32条只是事务分页，循环至本轮全部待分类候选处理完。禁止默认 call_copilot，不手改数据库或生成视图。无输入正常skipped；不能因为达到16条、8批或32条就将当日剩余工作留到次日。当天覆盖完成后再处理已授权的历史积压；近三周回审按日期记录覆盖，绝不把程序排除自动提示等同于真实内容已审阅。
5. 北京时间周日，在 daily 后执行 weekly；其他日期若最近应执行的周日之后没有 weekly 成功或正常跳过记录，也补跑。检查 runs，而非仅检查调度 lastFiredAt。读取 weekly_reflector.md，使用 weekly_rows/weekly_proposals/run_worker，由当前 pi 综合已接受的非敏感证据。证据不足返回空提案，不凑技能或公理。每周输入ID和处理进度由事务接口记录，不手改。
6. 检查所有遗留待审提案及本轮新草稿，逐项比较既有规则，核验可公开性与适用性。重复内容合并，工具细节留在工具层；记录每项落地文件、已有等效规则或具体证据缺口。不能停在生成草稿后就宣称维护完成，也不生成按日公开总结来替代知识归位。用户已持续授权本仓库安全整理产物完成后直接应用、提交并推送，无需逐次询问。只对敏感性不确定、权限扩大或实质性新决策停止并明确提问；不自动改变安全边界。应用完成再调用 resolve-review --decision applied --confirmed，不能用标记代替实际修改。
7. 本轮可公开产物做必要验证后，以明确文件列表 commit；每次 push（包括失败重试）前再次 fetch，检查是否有新的远端更新，快进或在原分支正常merge远端更新，恢复本地改动并重新验证；只有无法确定的语义冲突才保留现场并报告，不盲目推送。然后 push origin/main；不使用 git add . 或 -A，不夹带原有/并发修改、未知未推送提交，不强推、不自动变基。私有 .local、USER.local.md、原始历史、凭据、本机 .pi-loop.json 及锁文件排除。无公开变更不空提交。推送失败明确保留本地提交，不能声称同步成功。

## 完成标准

同一触发只由一个维护流程串行完成日整理和到期周整理，不再依赖两个同秒 cron 相互等待。检查 .pi-loop.config.json 的 recurringMaxAgeMs 为0。分别报告目标日期与扫描截止时间、当日真实对话总数/已审阅/待审阅、程序排除的自动提示数、保留首条的重复数、提炼与待分类数、历史积压、weekly实际结果和Git提交/推送；当天待审阅非零必须明确标为部分完成或阻塞，不能笼统说维护完成；输出具体哈希或失败原因，不把prompt已发送视作工作完成。

任务默认北京时间每天23:00。pi关闭时不执行；每台机器必须安装/恢复其本地任务并确认时区，Git推送不等于另一台机器已经运行。
