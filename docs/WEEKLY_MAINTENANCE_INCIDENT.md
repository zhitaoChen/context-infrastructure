# 周整理未执行：2026-10-18 事件核验

周任务在调度器中标记了触发，但没有进入本次会话，也没有执行 weekly。不是没有合格记忆，也不是 Git 落后导致 weekly 无法运行。随后助手只完成 daily，并把 weekly 留给另一个任务，未核对完成记录。这是调度交付与执行验收两个缺口。

## 直接证据

- 当时 daily 和 weekly 都配置为周日北京时间23:00；本机任务记录的 lastFiredAt 分别为 2026-10-18 23:00:00.022 和 .023，相差1毫秒。
- 本机对应 session 在23:00至23:05之间只有 daily 用户消息和其工具执行/最终回复，没有 weekly 用户消息。
- runs 表在当晚有 daily skipped，没有对应 weekly 运行。手动补跑于10月19日10:52成功：7条观察全部综合，1份提案，剩余未综合0条。这证明 weekly 并非因为无数据或验证接口不可用而未执行。
- 安装的 loop scheduler 在同一 check 循环内连续调用 sendUserMessage，不在首次发送后立即设置busy，也不等待交付或完成确认；发送后直接写 lastFiredAt。源码的 drainPendingFires 同样连续发送。
- 使用两个同刻到期的模拟任务和无副作用消息接收器复现：一次check连续发出两条消息，busy仍false，两条都标记已触发。此测试不调用真实模型，不创建真实任务。

## 根因与证据边界

已确认的实现缺陷是：两个同秒任务没有可靠的串行交付/完成机制，却都把发送动作记成触发成功。结合session缺失weekly消息，最合理解释是第二条消息在交付或会话路由环节未落入当前会话。没有宿主更底层交付日志，不能断言消息具体在哪一行丢失或是否曾路由到别处；lastFiredAt本身不能证明执行。

另一个确定原因是助手的执行验收遗漏：daily结束后明知周任务未执行，仍只报告应该稍后运行，而未检查数据库、补跑周整理。Git同步阻塞与私有周整理彼此独立，不应互相阻塞。

## 已实施修复

用一个每天23:00的持久任务替换原来的daily和weekly双任务。一个维护流程内串行执行daily，然后周日执行weekly；若上一应执行周日没有成功或正常跳过记录，后续维护补跑。周整理完成以runs事务记录验证，不依赖lastFiredAt。

执行规约保存于 `periodic_jobs/ai_heartbeat/prompts/pi_maintenance.md`，可经Git分发；本机任务ID和历史来源授权仍不上传。用户已授权本仓库安全整理产物不逐次询问，必要验证后直接应用、commit、push。隐私和权限边界保持不变。

未修改第三方loop扩展，本修复绕开已复现的同秒多消息机制；它仍属于pi会话内调度，pi关闭不运行。未来周日自动执行是否成功仍需实际运行记录验证，本次不宣称已验证尚未发生的自动执行。
